# VS Code Mind Map Extension — Project Instructions

Mind mapping custom editor for VS Code that operates directly on
`.md` files with true bidirectional sync. This is a port of the Obsidian
plugin at `/Users/burakucbinli/projects/obsidian` — that repo is the
reference implementation; consult its `DECISIONS.md` and `benchmarks.md`
before porting each area. Full plan:
[vscode-mindmap-extension-plan.md](vscode-mindmap-extension-plan.md).
Performance rules (below) **override any conflicting guidance in the plan.**

## Performance Rules (MANDATORY)

1. Performance is a top-priority requirement for this extension. Treat it as
   a hard constraint, equal to correctness.
2. Before implementing any feature, consider its performance impact on large
   mind maps (1,000+ nodes). Prefer incremental/O(changed) approaches over
   full recomputation.
3. **Decision protocol:** Whenever you face a trade-off between performance
   and ANY other concern — feature richness, visual fidelity, code
   simplicity, development speed, memory usage, sync granularity, library
   convenience — you MUST STOP and ASK the user which to prioritize.
   Never silently choose. Present the options, the performance cost/benefit
   of each, and your recommendation, then wait for the user's decision.
4. Never introduce a dependency without stating its bundle-size and runtime
   cost and getting approval if it is non-trivial (> ~50 KB min+gzip or any
   per-frame overhead).
5. After implementing each milestone, run the performance benchmarks
   (`benchmarks.md`) and report the numbers against the budgets before
   moving on.
6. Avoid premature *micro*-optimization, but never make *architectural*
   choices that block later optimization (e.g., full re-render on every
   keystroke, full re-parse of the md file on every change).
7. **VS Code-specific:** the webview and extension host are separate
   processes. The entire interaction loop (model, layout, render, keyboard
   handling, serialization) lives in the webview; the host is only the
   persistence layer. No interaction may block on a host round-trip.

Rule 3 is the most important one: **any performance-vs-anything trade-off
must be surfaced to the user as an explicit question, never decided
unilaterally.**

## Performance Budgets

| Metric | Target | Hard ceiling |
|---|---|---|
| Keystroke → node text update on screen | < 16 ms (1 frame) | 33 ms |
| Tab/Enter → new node visible & editable | < 50 ms | 100 ms |
| Fold/unfold branch (incl. rebalance animation start) | < 50 ms | 100 ms |
| Pan/zoom frame rate | 60 fps | 30 fps |
| Open a map with 500 nodes | < 300 ms | 700 ms |
| Open a map with 2,000 nodes | < 1 s | 2 s |
| Full relayout (auto-balance) of 2,000 nodes | < 100 ms compute | 250 ms |
| Markdown sync after node edit (write-back) | < 50 ms, debounced | — |
| Idle CPU usage (map open, no interaction) | ~0% | — |
| Memory for 2,000-node map | < 150 MB above baseline | 300 MB |
| Extension bundle size | < 500 KB | 1 MB |

Benchmark fixtures: 100 / 500 / 2,000 / 5,000 nodes (generated by
`scripts/generate-fixtures.mjs` into `fixtures/`, ported from the reference
repo). 5,000 is a stress test — degradation must be graceful, never a freeze.

## Process notes

- Log architectural decisions with performance implications in `DECISIONS.md`
  (choice, alternatives, measured/estimated cost). Where the reference repo
  already decided something (and the user approved it there), the decision
  carries over — note "carried over from reference" instead of re-litigating.
- Log per-milestone benchmark numbers in `benchmarks.md`.
- Manual verification happens in a real VS Code window (Extension
  Development Host, F5). jsdom/Node benchmarks don't paint pixels — report
  this limitation instead of claiming visual verification.
- No GitHub Actions workflow is used for this project — builds/releases are
  manual; don't introduce a `.github/workflows/` pipeline.
